# Druid SQL SFT dataset v2

Rebuild of the v1 dataset per `../druid_sql_dataset_v2_plan.md`. v1 scored well on its own validation
split but failed on real enterprise prompts: it invented column names and misused Druid functions in
shapes it had not seen, because it taught template recall rather than composition. v2 is built from
analyst-style questions over invented, realistic schemas, and **every gold answer is executed on Druid
35.0.0 and cleared by nine automatic gates**. The numbers for a given run are in `v2/dataset_report.md`
(regenerated by `make_report.py`); this file explains what the dataset is and how it was made.

No training or inference code was written or changed. `inference.py` and `lora_training.py` are untouched.

## The pipeline

```
schema_factory ──► seed data (3 independent copies per table, 18 months) ──► Druid 35.0.0
      │
      ▼
sampler ─► teacher LLM writes question + SQL ─► gates ─► dedupe / caps ─► split files ─► report
 (schema, style, time scope,   (Vertex AI Gemini,   G0 G2 G3 G5 G6 G7 G8 (text)
  complexity, features,         writer model)       G1 executes on Druid
  prompt format, length)                            G9 semantic judge, G4 independent 2nd answer
```

* **Schema factory.** 52 invented domain families (28 from v1, 24 drafted by the writer model and validated
  in code, `make_families_v2.py`), each realised as up to three datasources that differ in naming
  convention, width (7-200 columns), time-column encoding (six of them), and enrichment (multi-value,
  JSON, lookup, join partner). Columns carry semantic roles and polarity (`roles.py`); wide tables get
  near-duplicate column families (`created_by_id/name/email`), blank descriptions, nullability, allowed-value
  lists in descriptions, table overviews, per-table rules and a business glossary.
* **Seed data.** Each table is loaded three times with independent seeds (the `__g4b` / `__g4c` copies,
  never shown in prompts) so that a wrong query cannot match by coincidence. 2,400 rows per fact table over 18
  months, denser toward the present; NULLs, empty multi-value cells and malformed JSON are present.
* **Teacher.** Two different Gemini models through Vertex AI on the project's own billing: a pro-tier writer
  (`gemini-3.1-pro-preview`) and a flash-tier independent answerer / judge (`gemini-2.5-flash`) that never sees
  the gold SQL. The teacher is told the column roles and polarities, the value lists that exist, and today's
  date; it is told which values the schema text shows and must quote the rest verbatim.
* **Sampler.** Question style, time scope, complexity, feature families (only ones the schema supports),
  table count, prompt-length bucket, column-width tier and prompt format are drawn to hit the Section 7
  targets, with weights corrected for the gates' selection bias (categories that lose more to the gates are drawn more).

## The gates

| Gate | Check |
| --- | --- |
| G0 style | one statement, no fence/semicolon, every alias double-quoted, GROUP BY / ORDER BY by ordinal |
| G1 executes | runs on Druid 35.0.0 (on all three seeds inside G4) |
| G2 grounded | every column exists in a table the query actually reads (scope-aware: subqueries, CTEs, windows, UNNEST) |
| G3 literal fidelity | every filter value is recoverable from the question or the rendered schema text; a question naming a *different* listed value than the SQL uses is the v1 swapped-literal bug |
| G4 result agreement | an independent second answer returns the same rows on all three seeds, and the gold is non-empty on at least two |
| G5 role compliance | no SUM of a non-additive measure, no math on ids or category codes, no raw SUM/AVG of an epoch column |
| G6 instructions | deterministic: derived from the schema's own rules and glossary, not from what the teacher claims |
| G7 style truth | a "business" question names no column verbatim |
| G8 time phrase | "last month" is the completed calendar month, "past 30 days" a rolling window (Appendix A) |
| G9 semantic judge | a second LLM confirms grain, filters, window, direction and limit, on 100% of rows |

A gate rejection drops the example; nothing is patched by hand except in the hand-written set. Infrastructure
failures (Druid 502, API 429) are never recorded as rejections.

## Splits

Whole domain families are held out, not variants, so held-out splits share no vocabulary with train.
`splits.json` lists them: 40 train families (the 9 hand-written schemas are all train), and 4 each for
`val_heldout_domain`, `test_heldout_shape` (also drops any example whose SQL skeleton occurs in train) and
`test_prodlike` (4+ tables per prompt, wide tables, overview prose, rules and glossary, 10-25k tokens; its
distractor tables are drawn from every family, its targets only from its own). `assemble.py` fails if any
target family is shared between splits or a train/val/test prompt contains another split's tables.

`test_prodlike` must be hand-verified (plan Section 9). `v2/review_prodlike.html` is laid out for that; list
the ids you accept in `v2/prodlike_verified_ids.txt` and re-run `assemble.py` to set `meta.verified`.

## Addendum (F1-F6)

`druid_dataset_v2_addendum.md` fixed what an owner-side audit found: rules and glossary definitions were
templated. Everything that could be done in code was; Gemini wrote only the new rows. Order of the pipeline:
`assemble.py` -> (delete `v2_pre_addendum/` if you re-assembled) -> `glossary_terms.py --write` ->
`addendum_apply.py --extra add_defn_train add_defn_val add_defn_shape add_defn_prod add_decoy_train` ->
`make_report.py`. Numbers are in the "Addendum" section of `v2/dataset_report.md`; the conventions are in
`CONVENTIONS.md`. The SQL of an existing row never changes, so G1/G4/G9 were not re-run on it; row ids are stable.

## Reproducing

```bash
cd druid-harness && make up                      # Druid 35.0.0; broker heap is 4 GB (see docker-compose.yml)
cd ../dataset && export PYTHONPATH=$PWD/../druid-harness
../.venv/bin/python3 make_families_v2.py         # only to redraft the 24 extra families (committed as families_v2.json)
../.venv/bin/python3 gen_schemas.py              # schema_index.json, specs/, seeds/
../.venv/bin/python3 -u load_all.py              # resumable; ~1 h for 423 datasources
../.venv/bin/python3 verify_load.py              # independent check of what Druid holds
../.venv/bin/python3 curated.py                  # validate the hand-written rows -> curated.jsonl
../.venv/bin/python3 generate_v2.py --n 6000 --pool train --out train_pool --workers 16 --budget-usd 700
../.venv/bin/python3 generate_v2.py --n 350  --pool val --out val_pool --workers 6
../.venv/bin/python3 generate_v2.py --n 400  --pool test_shape --out test_shape_pool --workers 6
../.venv/bin/python3 generate_v2.py --n 350  --pool prodlike --out prodlike_pool --workers 6
../.venv/bin/python3 followups.py --base train_pool --n 320 --out followup_pool
../.venv/bin/python3 assemble.py && ../.venv/bin/python3 make_report.py && ../.venv/bin/python3 make_review_v2.py
```

Every generation command is resumable: rerun it and it continues. **The seed data is anchored to a date**
(`dataset_meta.json`); relative windows ("last 7 days") only return rows while the data is fresh. Regenerate
(`gen_schemas.py`, `load_all.py`) if the anchor is more than a few weeks old.

## Decisions taken (plan Section 11) and deviations

* **D1** unanswerable requests: the assistant output is `-- CANNOT_ANSWER: <what is missing>` (about 4%, four kinds:
  missing field, missing table, write request, near-miss). Two independent checks must both find nothing that answers it.
* **D2** output-wrapper variants: about 10% of train rows ask for one of five wrapper formats (JSON `sql` / `query`,
  JSON with a dialect field, fenced block, `<sql>` tags); the SQL inside passed every gate.
* **D3** the general-SQL mix-in was not built (the plan makes it the owner's call after the first v2 run).
* **D5** teacher models: Gemini 3.1 Pro (writer) and Gemini 2.5 Flash (independent answer and judge), via Vertex AI.
  The `GEMINI_API_KEY` in the environment is a free-tier AI Studio key (20 requests/day) and is **not** used.
* `md_sections` stays byte-identical to `prompt.py`'s serving renderer: it never carries notes, blank
  descriptions or reordered columns (`tests/` asserts this), so the one format that might be served is unpolluted.
* Twelve of the 14 prompt formats can carry table notes; `md_sections` and `bare` cannot.
* Question length is capped by complexity (median about 16 words), because real analyst questions are short.
* The hand-written set is the 64 v1 rows (re-validated; 12 were corrected because their question did not state what
  their SQL did, including the plan's `hw_ob_01`) plus 157 new ones, all cleared by every gate with G9 on 100%.

## Known limits

* **Data volume is small** (about 2,400 rows per table). Queries are validated for correctness, not performance.
* **Epoch-column unit suffixes** (`_ms`, `_epoch_s`) appear on slightly over 30% of epoch columns in the sampled
  train targets; the plan's cap is 30%. Changing it means renaming columns and reloading seeds.
* **Independent answers are model-generated.** G4 catches disagreement, not shared misreadings; the G9 judge and the
  human review packs are the backstop. `audit_sample.py` re-judges a random sample with the stronger model.
* **Glossary terms are arbitrary by construction** ("a *notable* build run is one where `branch_type` is `hotfix`"):
  they exist to teach rule-following, not domain knowledge.
* A `test_prodlike` row is only as good as its hand verification; `meta.verified` is false until you confirm it.
