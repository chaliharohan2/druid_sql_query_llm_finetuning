What to check

  • The template. Preamble + schema in system, bare SQL out. Expand it below and confirm it matches what you will serve.
  • The house style. Output aliases are always double-quoted, GROUP BY/ORDER BY use ordinals, relative time resolves against CURRENT_TIMESTAMP, and approximate aggregates are the default. If you disagree with any of those, now is the cheap moment to say so.
  • The traps. Hard traps are rejected by Druid; silent traps run clean and return the wrong answer. Both are shown with the real engine response.
  • Coverage. Is any quirk you hit in production missing from the cluster list on the left?

Single-table example — ds_sec_alerts, with a lookup
You write Apache Druid SQL. Return only the query. # Database Schema ## Table: `ds_sec_alerts` ### Columns: `__time` (TIMESTAMP): Detection time. Becomes `__time`. `alert_id` (VARCHAR): Alert identifier. `host_id` (VARCHAR): Host identifier. Resolvable through the `host_tier` lookup. `rule_name` (VARCHAR): Detection rule that fired. `severity` (VARCHAR): Severity: low, medium, high, critical. `src_ip` (VARCHAR): Source IP address. `dest_port` (BIGINT): Destination port. `bytes_transferred` (BIGINT): Bytes moved during the flagged activity. `alert_tags` (VARCHAR): Multi-value dimension. MITRE-style labels, e.g. persistence, lateral_movement. `analyst_verdict` (VARCHAR): Triage outcome: true_positive, false_positive, pending. `enrichment_json` (VARCHAR): JSON object stored as a string. Parse with PARSE_JSON before JSON_VALUE. Keys: asset_owner, env, patch_level. ### Lookups: `host_tier`: keyed by `host_id`. Maps host_id to its criticality tier: gold, silver, bronze. Use LOOKUP(host_id, 'host_tier').
Two-table example — ds_orders + ds_products
