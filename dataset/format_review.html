Druid Prompt Formats

Batch 01 rendered all 64 examples through one template, so the prompt was a constant — and a constant is exactly the sort of thing LoRA will happily bake in. These twelve renderers make the input a variable instead: the schema’s serialization, the preamble, the turn structure and the amount of prose all move independently of the SQL being taught. The assistant turn never changes. Bare SQL, no fence, no prose, in all twelve.

Not every format can carry every example

A terse format that drops column descriptions cannot tell the model which keys live inside a JSON string, and a format that never mentions lookups cannot support a LOOKUP() call. So each renderer declares what it is able to express, each example declares what it needs, and the sampler only draws from formats that cover it. Fifty-four of the sixty-four examples in batch 01 need nothing special and can be rendered by all twelve.

Knobs that turn inside each format

Format choice is the coarse axis. These four vary independently underneath it, so two examples rendered through the same format still do not look alike. None of them are in the code yet — they go in when I generate the full set, assuming you want them.

Distractor tables

Roughly a quarter of prompts carry one or two extra tables the query never touches. Real schema blocks get dumped wholesale, not curated down to the answer.

Column order

The time column is not always listed first, and columns are not always in ingest order, so position never becomes a cue for which column is the timestamp.

Description density

Within the formats that carry prose, some columns get a full description, some a fragment, some nothing at all. Real catalogs are patchy.

Table naming

The ds_ prefix drops off a share of the schemas, and some use camelCase columns, so no single naming convention gets welded to the dialect.

Two things I need you to settle

Which format does inference use? Whatever ends up in inference.py should be the heaviest one in the mix, and right now that is md_sections at 22 percent. Training across twelve formats buys robustness to a prompt you have not written yet; it does not buy you the right to serve a thirteenth. If you plan to ship a different one, tell me which and I will re-weight before generating.

Format diversity is only half of the fix you asked for. These twelve vary the shape of the prompt, but all four cases above still describe the same nine datasources. A model that has seen ds_sec_alerts two hundred times can memorize its columns no matter how they were serialized. For the 1000-example set I plan to generate around sixty schemas from domain templates, hold a disjoint set of them back for validation, and cap any single schema at about three percent of the data. Raising it because it is the same failure you spotted, one level down.
